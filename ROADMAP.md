# LMS roadmap

The LMS is the company's internal Learning Management System, where employees find and complete training and admins and instructors author courses.
This is our product roadmap: what works today, what we build next, the features after that, the work needed before production, and the decisions still open. Sizes are explained at the end.

## Working today

Course authoring is the only feature so far (spec: [`docs/course-authoring.md`](docs/course-authoring.md); infrastructure: [`infra/lib/lms-stack.ts`](infra/lib/lms-stack.ts); CI: [`.github/workflows/ci.yml`](.github/workflows/ci.yml)).

**All of this works in local development only.**

- A deployed web build sends no token: `authToken()` in `apps/web/src/api/client.ts` returns `undefined` outside dev, so the API answers 401 to every call except the public health check.
- Deploys don't apply database migrations (see "Not wired yet" below).
- There is no automated deploy: CI only checks that the infrastructure code builds, and a deploy is a manual command run from `infra/`.

What works locally:

- Admins and instructors create courses (title, description) made of ordered lessons:
  - **text**: plain text with line breaks kept;
  - **video**: an https URL. `.mp4`/`.webm`/`.ogg` play inline, YouTube and Vimeo embed, and any other URL shows as an "Open video" link;
  - **document**: an https URL that opens in a new tab.
  - Video and document lessons can have optional notes; any lesson can have a duration (1–600 min).
- Authors add, edit, delete and reorder lessons (up to 200 per course), and the API validates every field and rejects unknown ones.
- Authors publish a course (it needs at least one lesson) and can unpublish it. Only unpublished courses can be deleted, and a published course can't lose its last lesson.
- Instructors manage only their own courses, and admins manage all of them. Other users get a 404 for drafts, so draft IDs don't leak, and learners can't open the Manage pages.
- Any signed-in user can browse the catalogue of published courses (newest first), open a course and read its lessons with previous/next.
- The API verifies sign-in tokens from our identity provider:
  - it accepts only **ID** tokens, and only for the one configured app client;
  - roles come from the token's groups (`admin`, `instructor`, `learner`), and unknown groups are dropped;
  - it creates the user on first sign-in and syncs roles from the token when they change;
  - user identity is the identity provider's subject (stored as `externalId`). Emails are not unique: a user deleted and re-created in the identity provider with the same email gets in as a new LMS user, and rows are never relinked by email (`apps/api/src/users/users.service.ts`);
  - the stored email changes only when the token's email is verified.
- The web app has a dev-only "Sign in as" switcher with four seeded users, and it is not rendered in production builds.
- Seed data: 4 dev users, 2 published courses and 1 draft.
- Infrastructure as code (`infra/`): one stack per stage, in a UAE region by default, with:
  - a private network;
  - managed Postgres, encrypted at rest (a standby in a second availability zone, deletion protection and 14-day backups in prod). The API reads the database credentials from the secrets store and connects over TLS;
  - the API in container hosting behind a load balancer (two containers in prod, one in other stages), with automatic rollback when a new version fails its health checks;
  - a user directory (the identity provider the API trusts) with admin, instructor and learner groups and no self sign-up;
  - private file storage and a content delivery network for the web app, with `/api/*` routed to the load balancer.
- CI (GitHub Actions) runs format, lint, typecheck, tests (the API integration tests against a real Postgres), build and an infrastructure build check, and builds the API container image. It does not deploy.
- Not wired yet:
  - sign-in with the identity provider in the web app (only the dev switcher exists);
  - running `prisma migrate deploy` on deploy;
  - deploying the web build (uploading it to file storage and clearing the content delivery network's cache);
  - a custom domain;
  - HTTPS between the content delivery network and the API, and keeping the API's load balancer private. Today the load balancer is internet-facing on plain HTTP (port 80, open to any address), so the API can be reached directly, bypassing the content delivery network;
  - production database sizing: every stage, prod included, uses a small burstable database instance with 20 GB of storage;
  - an outbound internet gateway (NAT) in each availability zone: there is a single one;
  - MFA: the user directory has none.

## Next up

Five priorities, in build order. Items 2, 3 and 5 all change `schema.prisma`; if two are built at the same time, the one that merges later regenerates its migration on top of the merged schema instead of merging migration folders by hand.

### 1. Sign-in with the identity provider in the web app (feature 1.1, S)

- **Scope:**
  - Sign in and sign out through the identity provider's hosted sign-in page (authorization code + PKCE), with tokens kept in memory and refreshed silently. The web app sends the **ID token**, because the API accepts only ID tokens.
  - Infrastructure: a sign-in domain for the user directory, and OAuth settings on the existing web app client: code flow only, `openid email profile` scopes, and callback and sign-out URLs for localhost and the web app's URL. Today the client has default OAuth settings (code and implicit flows, a placeholder callback URL) and the directory has no sign-in domain, so it can't be used yet. Keeping one client means the API's single client-ID check still matches; a second client would need the API to accept both client IDs.
  - A script creates one test user per role and adds it to its group, and a test shows that a learner signed in this way can't open Manage.
  - The dev switcher stays for local development only.
- **Why now:**
  - The API half already exists, so this is mostly web and infrastructure work.
  - Nothing can be used outside local development without it, and every later feature can then be tested with real users and roles.
- **Depends on:** nothing to start. Using it on the deployed web app also needs migrations on deploy (P3) and the web deploy (P4). Which hosted sign-in options we can use is Q6.

### 2. Lesson file upload with private delivery (feature 2.1, M)

- **Scope:**
  - Instructors upload PDF, PPTX, DOCX and MP4 files from the lesson editor instead of pasting a URL. Files go straight from the browser to private, encrypted file storage through short-lived signed upload URLs.
  - Limits: PDF, DOCX and PPTX up to 50 MB, MP4 up to 500 MB. The API checks the file extension and content type before it signs the upload, and the signed upload enforces the size.
  - Learners open files through signed links that expire after a few minutes. Serving them through the content delivery network waits until Q9 (edge caching outside the UAE) is answered.
  - Lesson model and spec change: a video or document lesson holds either an https `url` (as today) or a file key with its file name, type and size. The lesson validation and `docs/course-authoring.md` change with it.
  - Video transcoding (2.3) comes later.
- **Why now:**
  - Authors stop linking to public URLs.
  - The course draft from a document (4.3), CSV import (1.4), certificates (6.1) and the video pipeline (2.3) all reuse it.
- **Depends on:** 1.1. Malware scanning (P10) must ship before any production use.

### 3. Enrolment, assignment and progress (features 3.1–3.4, S + M + M + S)

- **Scope:**
  - One spec for the data model (enrolment, assignment, lesson progress) and the progress interface the dashboard reads (status, % progress, last lesson and video position, completion date). After that the work splits into two parts that can be built in parallel:
    - enrolment and assignment: self-enrolment (3.1), assigning a course to named people with a due date and a mandatory flag (3.2), and the My learning dashboard (3.4), built against the progress interface;
    - progress: lesson completion rules (Mark as complete, inline video complete at about 90% watched), resume position, % progress and the course completion date (3.3).
  - Assigning by department, grade or role waits for employee profiles (1.4).
  - Rules the spec must state:
    - A due date is a calendar date in Asia/Dubai. An assignment is overdue from the next day (00:00 Asia/Dubai).
    - Watch % can be measured only for inline `<video>` files (`.mp4`/`.webm`/`.ogg`). YouTube and Vimeo embeds need their player APIs (later), so until then they, "Open video" links and document lessons use Mark as complete.
    - Lessons added to a published course that has enrolments: learners who have already completed the course stay complete; for everyone else the new lesson is required, and % progress is recalculated. Lessons deleted: their progress no longer counts, and a learner who has now completed every remaining lesson is marked complete. Re-completion rules for changed content come with course versioning (6.5).
    - A course with enrolments can't be deleted; unpublish it instead.
- **Why now:**
  - It is the core of the LMS. Reminders, certificates, reports, the manager view and the Zella bot all need it.
  - It runs on the existing stack and needs no access or approval from other teams.
- **Depends on:** 1.1 for real users (the dev switcher stands in until then). Managers assigning to their own team needs roles (1.2) and profiles (1.4).

### 4. AI course draft from a document (features 4.1 + 4.3, S + M)

- **Scope:**
  - An AI gateway module in the API (4.1) that wraps the AI model's API. It holds the model ID per feature in config, versioned prompt templates, JSON-schema output validation, timeouts and a fake client for tests, and the infrastructure code gives the API permission to call the model.
  - An instructor uploads a text-based PDF or DOCX (through file upload, 2.1) and gets an **unpublished** draft course with a title, description, objectives and 3–10 text lessons, each noting its source, which opens in the existing editor. If 2.1 is not ready, the API can take the file directly (up to 10 MB, processed in memory and not stored) and move to 2.1 later.
  - Text extraction: a per-page PDF parser (e.g. `pdfjs-dist`) keeps page numbers, so each lesson can cite its source pages. DOCX files have no fixed pages, so DOCX lessons cite source headings instead. Sending the whole file to the model is the alternative, but page citations are then not guaranteed.
  - Until guardrails and the usage log (4.2) exist, we use only non-confidential documents.
  - Scanned PDFs and PPTX come later.
- **Why now:**
  - It builds directly on course authoring that already works, writing to the existing Course and Lesson tables.
  - It cuts the effort of turning existing policies into courses, and a person always approves the draft.
- **Depends on:** Q1 (which AI model, and where the data is processed) answered and signed off by compliance; 2.1 to keep the source file.

### 5. Quiz lessons with AI-drafted questions (features 5.1 + 5.2, M + M)

- **Scope:**
  - A new `quiz` lesson type: a `LessonType` enum migration, validation rules for questions and options, and a quiz renderer in the lesson viewer.
  - Single-choice (exactly one correct option), multiple-choice (one or more correct options) and true/false questions, a pass mark, a maximum number of attempts and server-side scoring.
  - Multiple-choice questions are scored all-or-nothing: a question counts as correct only when the learner picks exactly the correct options.
  - The course completes only on a pass, through the completion rules from item 3.
  - Then "Suggest questions" on a lesson (5.2), through the AI gateway (4.1). It returns draft questions with the correct answer, an explanation and the source lesson, and the instructor approves each question before it is saved.
- **Why now:**
  - It gives evidence that learners understood the content, not only that they opened it.
  - Its acceptance criteria are easy to test (attempt limits, pass logic, all-or-nothing scoring for multiple-choice, no question saved without approval), and the AI part reuses the gateway from item 4.
- **Depends on:** 3.3 for completion; 4.1 for AI-drafted questions.

## Open questions

Decisions we still need to make. The sections above refer to them by their Q numbers.

1. **AI model and where data is processed (Q1).** Which text and embedding models do we use? Can employee and course data be processed in the UAE, and if a model is only available elsewhere, which locations process the data and is that acceptable? What usage quotas do we get? Needed before the AI gateway (4.1).
2. **AI guardrails (Q2).** Which guardrails can we use where the data is processed: content filters, PII masking and a grounding check for the course assistant? Can they detect Emirates ID numbers, or do we use a custom pattern filter?
3. **Retrieval store (Q3).** For the course assistant and search by meaning, do we use pgvector in our existing Postgres or a managed retrieval service?
4. **Arabic speech-to-text, OCR and translation (Q4).** Which services handle Gulf Arabic in training videos, scanned and Arabic PDFs, and Arabic translation well enough, and where do they process data?
5. **AI cost (Q5).** What will the AI features cost per month at our headcount and peak usage (figures from P17), and what budget and alert thresholds do we set?
6. **Identity provider (Q6).** Which company identity provider do we federate with, over SAML or OIDC, and who in IT registers the app? Which plan of our identity provider do we need for hosted sign-in, MFA and threat protection?
7. **Data residency (Q7).** Which data must stay in the UAE, which exceptions are acceptable (email sending, AI processing, edge caching), and who signs off for security and compliance?
8. **Email (Q8).** Which email service do we send from, and from which location? Does it need approval before we can send to every employee, and how long does that take? How do DKIM and SPF for the LMS sending domain work alongside our existing corporate mail setup?
9. **Edge caching (Q9).** The content delivery network caches files at edge locations outside the UAE. Do we turn edge caching off for sensitive documents and certificates?
10. **Service availability (Q10).** Which of the managed services we plan to use (job scheduler, email service, video transcoding, malware scanning, container image scanning, tracing, synthetic checks, backups, database connection proxy, private endpoint to the AI model) are available in our region with the features we need?
11. **Cloud accounts (Q11).** Does the LMS get its own accounts under the company's existing cloud organisation, and who provisions them? Which global services must be exempt from the region policy (P21)?
12. **Video pipeline (Q12).** For v1, are MP4 files behind short-lived signed links enough for mostly short training videos, or do we go straight to adaptive streaming (HLS)? If HLS, how do we protect the streams (e.g. signed cookies)?
13. **SCORM (Q13).** Does any bought-in content arrive as SCORM? If so, do we use an open-source SCORM runtime or a hosted SCORM service, and how do we launch packages from the same origin as the app?
14. **Retention and privacy (Q14).** What retention periods apply to training records, certificates, AI call logs and leavers' data, and does UAE PDPL apply? Needs legal and HR.
15. **Disaster recovery targets (Q15).** What RPO and RTO do we commit to for the LMS?
